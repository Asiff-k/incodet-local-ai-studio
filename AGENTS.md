## What Lovable manages

Rules outside this block are the project's own. Change the pieces below in
Lovable, not by hand. With the [Lovable MCP](https://mcp.lovable.dev)
connected, `send_message` asks Lovable to do it; otherwise ask the user to
use the editor.

- **Database.** Do not add or edit `supabase/migrations/` or `drizzle/`.
  Ask Lovable to change the schema.
- **Generated files.** Do not edit a file whose header says it is automatically
  generated.
- **AI gateway.** Keep model calls on Lovable's gateway, and keep
  `LOVABLE_API_KEY` out of browser code.
- **Connectors.** Lovable provides native connectors. `list_connectors` shows
  which are enabled; `add_connector` only returns the dashboard link. When a
  connector is enabled, calls go through the connector gateway and need
  `LOVABLE_API_KEY`. When Lovable does not provide one, users can bring their
  own key and store it in Secrets.
- **Secrets.** Lovable manages them. Do not put secret values in the repo.

- Contact details, socials and hero media live only in src/config/site.ts; components read from it so brand data changes in one place.
- Shared site UI lives in src/components/site; typography utilities are named type-* (not text-*) so they never clash with color classes in cn/tailwind-merge.

- Industry pages share one template (src/components/site/IndustryPage.tsx) fed by src/content/industries.ts; add industries by data, not new layouts.
- Case study detail pages are data-driven from src/content/caseStudies.ts and render only sections that have data.
- Contact form submissions go through the `submitContact` server function (src/lib/contact.functions.ts), which inserts with the admin client; contact_messages has no public insert policy so spam checks cannot be bypassed.
- Owner notification emails use Resend directly only when the RESEND_API_KEY secret exists; without it the row is saved and sending is skipped, so the form never depends on email.
- Portal access is granted only by the database: link_user_by_email (run by an auth.users trigger and the claim_portal_access RPC) assigns admin from admin_allowlist and client from clients.email; never assign roles from client code.
- Clients never insert payments directly; "I've paid" goes through reportPayment (src/lib/portal.functions.ts), which checks invoice ownership via RLS before the admin insert.
- Portal demo data lives only in src/content/demoPortal.ts and the dashboard UI (src/components/portal) is shared between demo and live via props.
- Public page heads use seoHead(title, description, path, opts) from src/lib/seo.ts so canonical, Open Graph, Twitter and JSON-LD stay consistent; the base URL is site.siteUrl.
- Every route declares staticData.sitemap; /sitemap.xml is built from the router plus case study data, so new public pages only need sitemap: true.
- Analytics scripts are injected only by CookieConsent after Accept, and the banner renders only when site.analytics has a provider and id.
- Case study device mockups are generated by scripts/mockups (capture.py then compose.py) into public/images/mockups; rerun the scripts instead of editing images by hand.
- Every project is its own case study in src/content/caseStudies.ts; the work carousel reads `showcase`, which only takes projects with a liveUrl, so unlinked internal tools can never appear.
